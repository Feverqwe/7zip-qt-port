# Regression strategy

Для изменения поведения выбрать сценарий в [regression matrix](regression-matrix.md),
найти его suites в каталоге ниже и проверить текущие public API/callers.
Требования к regressions, fixtures и focused/full checks — в
[AGENTS.md](../AGENTS.md#validation-and-ui-reference); команды и opt-in slow suites —
в [development](development.md#local-commands).

## Каталоги покрытия

- [Поведение и suites](testing/coverage.md): поиск по CTest name, классу или ID.
- [UI и геометрия](testing/geometry.md): producer targets, состояния и widget JSON.
- [UI contracts](ui-layout-contracts.md): требования к конкретному виду.

Каталоги содержат накопленные свидетельства разных ревизий. Сопоставлять их
с текущими tests/CMake и кодом; старое PASS или «unverified» не определяет
текущую приёмку. Датированные результаты новых запусков писать в
[source audit](upstream-port-audit.md), а здесь менять описание покрытия.

```sh
rg -n -F 'archive_transfer' docs/testing/ tests/ docs/regression-matrix.md
./scripts/build.sh dev <targets>
./scripts/ctest.sh --preset dev -R '<regex>' --output-on-failure
```

## Выбор объёма проверки

По умолчанию агент собирает затронутые targets и запускает suites для изменённого
сценария и его прямых consumers. Для локального изменения достаточно этих проверок;
завершение задачи или коммит не требуют полного прогона. Общий адаптер требует
проверки использующих его компонентов, изменение test wrapper — его собственных
регрессий и затронутого способа запуска, изменение сборки — затронутых targets.
Один исправленный тест не заменяет проверку остальных затронутых сценариев.

Перед запуском кратко назвать выбранные проверки и связь с изменениями.
Расширять набор при выявленном влиянии на другие компоненты или сбоях.
Критерии полного gate и opt-in долгих suites задаёт
[AGENTS.md](../AGENTS.md#validation-and-ui-reference). В результате перечислить
выполненный scope и непроверенные платформы; focused PASS не означает full PASS.
Для правок только документации и инструкций достаточно `git diff --check`.

## Test artifact retention

Перед новой серией проверок агент осматривает остатки завершённых запусков и
удаляет воспроизводимые временные данные своей задачи. Это правило работы
агента; `build.sh`, `ctest.sh` и `check.sh` сами старые запуски не удаляют.

- Использовать существующий `build/dev` или `build/release`, если не нужна
  изоляция toolchain/snapshot. Сохранять incremental outputs, compiler cache,
  загруженные инструменты и зависимости: их удаление замедляет проверки.
- Одноразовые fixtures, распаковки, staging и диагностические файлы создавать
  в отдельном каталоге задачи и удалять после успешной проверки. Перед следующим
  запуском убирать оставшиеся данные уже завершённых попыток этой задачи.
- В `ui-reports/` и task-owned каталогах снимков сохранять актуальный набор для
  review, нужный reference и данные неразобранных сбоев; удалять только заведомо
  устаревшие результаты. Скриншоты создавать лишь по правилам AGENTS.md.
- Старые `sevenzip-script.*` и другие временные логи удалять только после
  установления принадлежности завершённому запуску. Логи текущего сбоя сохранять
  до разбора; успешные buffered logs уже удаляет `agent-output.sh`.
- Перед удалением проверить точные пути, процессы и ссылки текущих задач.
  Возраст файла или совпадение префикса сами по себе не доказывают, что он лишний.
  Не очищать весь `/tmp`, все `build/`, `.codex/`, чужие задачи или рабочее дерево.
  Если принадлежность неясна, оставить данные и сообщить об этом.

Для удалённых snapshots действует [runner retention](hyperv-runners.md#storage-policy-user-instruction-2026-10-07):
три последних запуска, активные/referenced runs и нужные evidence сохраняются;
у более старых завершённых запусков удаляются тяжёлые воспроизводимые данные,
но остаются небольшие логи и metadata. Кратко фиксировать удалённые пути;
при нехватке места — также свободное место до и после очистки.
