# Актуализация поддержки ZIP

Дата исследования: 2026-10-24. Ветка: `feature/zip-refresh`, исходный commit:
`ea4f728c`. Goal относится к формату ZIP в приложении; обновление всего 7-Zip
не является его целью. Этот документ фиксирует предварительный выбор и план,
а не завершённую реализацию или runtime-приёмку.

## Цель и условия завершения

Актуализировать чтение, создание и изменение ZIP без потери существующих
возможностей. Сравнить поддерживаемые библиотеки с текущим обработчиком;
замена оправдана измеримой пользой и подтверждённой совместимостью.
Регулярные обновления зависимости должны быть воспроизводимы по существующей
[процедуре обновления](upstream-update.md).

До изменения реализации нужны проверенные сценарии открытия, просмотра,
проверки целостности, извлечения, создания, обновления, удаления,
переименования и изменения комментариев. Для каждого сценария отделить
доступное в интерфейсе поведение от возможностей самого engine.
Сохранить пароли, отмену, сообщения о неполном результате, проверку путей
извлечения и неизменность источника при ошибке или отмене.

## Исходное состояние

На момент создания ветки baseline 7-Zip была 26.04,
`9128b80e3a471108678e2b3ec3c985861c8d7b0f`.
Текущий ZIP уже реализован библиотечным кодом официального engine;
переход на другую библиотеку сам по себе не устраняет устаревание зависимости.
Исходные owners — `CPP/7zip/Archive/Zip/`, их codecs/crypto/stream dependencies;
статический consumer задан в `cmake/native_zip.cmake`.
Нужно отдельно учитывать native runtime, которым пользуется приложение.

Первичный просмотр dispatch в `ZipHandler.cpp` подтверждает отдельные пути
Shrink, Implode, LZMA, XZ, PPMd, Zstandard и LZFSE, а также обращение к registry
для других методов. Это свидетельство исходного кода, а не runtime-подтверждение
каждого метода. В UI создания ZIP предлагаются в том числе Deflate64 и PPMd.
Нельзя считать перечисление имён методов доказательством возможности декодирования.

Существующие `native_zip_writer_tests` проверяют изменение комментария, сохранение
данных/свойств и источника, AES, Unicode, ошибки записи и отмену.
`archive_recovery_backend_tests` — один из прямых consumers для проверки
повреждённых архивов. Эти проверки следует переиспользовать, дополняя только
выявленные пробелы поведения.

В основном checkout на момент создания ветки есть незакоммиченные изменения
ZIP/Shrink и общего обновления 26.05 вместе с другими задачами. Они не перенесены
в эту ветку и не являются её принятыми результатами. Перед реализацией нужно
сверить их актуальный статус, чтобы не дублировать и не затереть чужую работу.

## Предварительное сравнение

### Эталоны

По решению пользователя от 2026-10-24 проверка разделяется по назначению:

- [PKWARE APPNOTE 6.3.10](https://pkware.cachefly.net/webdocs/casestudies/APPNOTE.TXT)
  — опубликованная спецификация контейнера, ZIP64, каталога и томов.
- [WinZip AE-1/AE-2](https://www.winzip.com/en/support/aes-encryption/)
  — спецификация WinZip AES.
- Официальный 7-Zip — библиотечная основа и источник обновлений реализации.
- libzip, minizip-ng и libarchive — независимые сравнения совместимости
  для поддерживаемых ими сценариев; ограничения одного из них не определяют
  допустимый набор функций приложения.

Linux используется для общих декодеров по уже существующим аудитам.
В [аудите Linux](upstream-port-audit/filesystems-linux.md) отдельно установлено
отсутствие ZIP container parser в выбранном kernel reference.
Прежние изменения Zstandard/XZ/LZMA уже подключены к ZIP; доступ к повреждённым
ZIP описан в [аудите recovery](upstream-port-audit/read-only-access.md).
Это частичная актуализация общих компонентов, а не обновление всего контейнера.

### Кандидаты

| Вариант | Польза | Препятствие для полной замены |
| --- | --- | --- |
| Обновлять ZIP closure официального engine | Сохраняет текущие интерфейсы и широкий набор методов | Нужно проверять зависимости и согласованность статического consumer с runtime |
| libzip | Специализированный C API; создание/изменение ZIP, ZIP64, AES; атомарная замена архива | Многодисковые ZIP явно не поддерживаются; равенство набора методов текущему engine не подтверждено |
| minizip-ng | ZIP64, AES, split archives, несколько современных методов, восстановление central directory | В опубликованном наборе возможностей нет Shrink/Implode/Deflate64; равноценная замена этих путей не установлена |
| libarchive | Потоковая работа и широкий набор форматов | ZIP поддерживает ограниченный набор методов; PPMd только для чтения, другие методы вне документированного набора не поддерживаются |

Источники, проверенные 2026-10-24:

- [libzip: назначение и возможности](https://libzip.org/),
  [атомарное изменение](https://libzip.org/documentation/libzip/),
  [ограничение multi-disk](https://libzip.org/documentation/zip_errors/),
  [методы записи](https://libzip.org/documentation/zip_set_file_compression/).
- [minizip-ng: возможности и параметры сборки](https://github.com/zlib-ng/minizip-ng/blob/develop/README.md).
  Набор возможностей development-ветки не заменяет проверку выбранного stable commit.
- [libarchive: официальное описание ZIP](https://github.com/libarchive/libarchive/blob/master/libarchive/libarchive-formats.5).

Решение пользователя от 2026-10-24: использовать официальный ZIP handler
7-Zip как библиотечную основу и дополнять его при необходимости. Обновлять
выбранный компонент с необходимыми зависимостями; сохранять пригодный
upstream-код, локальные исправления и возможности приложения. Перед дополнением
проверять, нет ли готового решения в upstream; новые возможности определять
по конкретным пробелам, а не по одному перечню из спецификации.
Операции остаются за `ArchiveBackend` и официальным native engine.

## Порядок дальнейшей работы

1. Завершить сравнение полных тел reader/writer/update, callers, codecs, crypto,
   volumes, extra fields, кодировок и recovery. Использовать существующий
   [source audit](upstream-port-audit.md), без нового параллельного реестра.
   Сопоставить ZIP-возможности с актуальной спецификацией и источниками engine;
   отделить отсутствие функции от ограничений приложения и параметров сборки.
2. Зафиксировать выбранные upstream commits и полный diff относительно baseline,
   включая зависимости и уже подготовленные локальные исправления.
   Для внешнего импорта использовать существующий manifest с SHA256 оригиналов,
   mapping и аудитом причин адаптации. На этапе исследования код не импортирован.
3. Выполнить обоснованные изменения ZIP и подключить их к реальному native
   consumer. Обновление остальных форматов не включать автоматически;
   необходимые общие зависимости оценивать отдельно.
4. До приёмки повторно сравнить изменённый scope с оригиналом. Запустить focused
   проверки успеха, ошибки и отмены, паролей, Unicode/пробелов, метаданных,
   томов и доступного чтения повреждённых ZIP, а также небезопасных путей.
   Добавлять тест только для конкретного риска, который не покрыт существующими.
5. Проверить macOS; при платформенных изменениях — также Linux и Windows.
   Зафиксировать отдельно source completeness, runtime evidence и непроверенные
   сценарии. Slow suites запускать только по явному запросу.

Первая итерация выполнена: официальный ZIP dependency closure сверён с 26.05,
изменённые Shrink units перенесены и подключены к native runtime.
Прежние общие декодеры и recovery сохранены. Source scope, provenance,
focused macOS evidence и непроверенные сценарии — в
[аудите этой итерации](upstream-port-audit/zip-refresh.md).
Сравнение библиотек выше служит архитектурному выбору; runtime interoperability
с ними и полная приёмка всех ZIP extensions не выполнялись.

После rebase на `master` (`c88700e1`) вся baseline уже 26.05.
Официальный Shrink и runtime/cache исправления входят в базовый коммит;
их повторный перенос и selective overrides не нужны. Ветка добавляет
выбор эталонов и проверки изменения разрядности Shrink до 10/13 бит.

Следующая реализация по запросу пользователя — создание и обновление ZIP
методом Zstandard (93) на официальном libzstd с сохранением handler 7-Zip.
Её source scope, решения по adapter и актуальные результаты собраны в
[ZIP encoder audit](upstream-port-audit/zip-zstd.md); decoder migration
и поддержка всех ZIP extensions не входят в эту реализацию.
